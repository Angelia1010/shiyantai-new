# 503 标准试验台数字化校验系统

燃油泵标准试验台的数据监控与故障诊断平台：实时监控试验台导出的数据文件，计算特征并在三维/二维模型上展示，用流量计互校、质量-体积校核与仿真模型（健康参考模型）对比做诊断并归纳原因，生成 Word 诊断报告；另提供基于本地大模型的数据分析与问答。

## 架构

```
浏览器 ── digital-twin-platform（Vue 2 + Element UI）
   │  /api/task   ──►  任务服务     pump_test_bench/app/services/task_service.py   :5001  登录、任务、诊断、报告、仿真模型
   │                        └─ 重建仿真基准表（AMESim 模型时）──►  AMESim 服务  AMESim_server/src/AmeSimuSessionServer.py  :5003
   │  /api/file   ──►  文件服务     pump_test_bench/app/services/file_service.py   :5002  列文件、分页读取、实时监控、自动诊断
   └  /api/ai     ──►  大模型服务   pump_test_bench/app/services/llm_service.py    :8999  数据分析与问答 ──► Ollama
```

- 开发时由 `vue.config.js` 的代理转发 `/api/*`，生产环境由 Nginx 转发（`deploy/nginx.conf`）。
- 所有后端默认只监听 `127.0.0.1`；除 `/health` 与登录接口外都要求请求头 `X-Token`。令牌由任务服务签发，各服务用同一个 `SECRET_KEY` 校验。
- 数据目录在前端填写（工作台“数据目录”、自动诊断配置页），后端校验后登记到 `pump_test_bench/data/data_dirs.json`，
  所有服务共用；`.env` 的 `DATA_ROOTS` 只是可选的预置目录。接口只能访问预置或登记过的目录，
  登记时要求目录存在且不是磁盘根目录或系统目录；文件名可以带子目录，但不能跳出该目录。

### 实时监控（`pump_test_bench/app/core/live_monitor.py`）

试验台通过文件共享把数据写到一个目录，系统这样对接：

1. 在工作台右上角“数据目录”里填写该目录的完整路径（也可在“自动诊断”实时模式中填写），
   目录会自动登记并保存到 `pump_test_bench/data/live_monitor.json`，文件服务重启后自动恢复。
2. 文件服务每 `LIVE_SCAN_SECONDS` 秒扫描一次目录（含子目录）。用定时扫描而不用文件系统通知，
   是因为网络共享（SMB）上的变化通知不可靠。
3. 正在变大的文件只读新增的完整行（没写完的半行留到下次），按时间列每 1 秒聚合成一帧（max/min/avg）。
4. 工作台每秒取一次新帧（`/live/frames`），延迟约 1–2 秒，与“自动诊断”页面是否打开无关，任何电脑都能看。
5. 文件停止变化 `LIVE_SETTLE_SECONDS` 秒后视为写完，发布“文件完成”事件，自动诊断据此处理整个文件。

没有试验台时可以用回放工具模拟“边测边写”：

```bash
# 然后在工作台“数据目录”里填写目标目录的完整路径
python -m pump_test_bench.tools.replay_data pump_test_bench/samples/标准台样例 --to 数据/实时 --speed 1 --loop
```

### 数据文件格式兼容（`pump_test_bench/app/core/table_parser.py`）

文本文件（.txt / .csv）不假设固定格式，逐项自动识别：

- 编码：UTF-8（含 BOM）、UTF-16、GBK/GB18030；分隔符：制表符、逗号、分号、竖线或连续空白；
- 表头：没有表头（试验台软件偶尔会把表头覆盖掉）时，先借用同目录中列数相同的文件的表头，
  再按列数匹配 `app/core/known_headers.py` 中的标准表头（试验台软件升级后列数/顺序有变化，在这里追加即可）；
- 任意位置的空行、行尾多余的分隔符、文件中途重复的表头行；
- 分隔符个数不足的行（没写完或被覆盖的残行）丢弃并计数，不影响其他行；
- 列名全角转半角，末尾括号里的单位单独记录（如“供油压力1-1(MPa)”）；
- 时间：`时:分:秒.毫秒`、`分:秒.毫秒`、不补零写法（`17:3:36.243`）、带日期前缀，跨午夜/整点自动接续。

### 诊断（`pump_test_bench/app/diagnosis/`）

**何时诊断**：实时监控时，数据文件写完后由文件服务在后台自动诊断（任务类型“自动诊断”，可在工作台“数据目录”
或“自动诊断”页开关）；也可以在“自动诊断”页选择文件批量诊断。

**怎么诊断**（`engine.py` → `flow_loop.py` → `reconcile.py` / `isolation.py` / `changepoint.py`）：

1. 识别稳定段：按 1 秒窗口找流量最平稳的最长一段（起停、换工况的过渡数据不参与判断）。
   **找不到稳定段**时用全部数据分析；若没有发现明确的故障，结论为“无法判定”，而不是“正常”；
2. 传感器自检：卡死/冻结、掉零、无数据、超量程、噪声、毛刺，同位置两只温度传感器互校。坏掉的表不参与后面的比较。
   已知损坏的测点（如 T6、T7）在 `bench.json` 的 `ignored_sensors` 中屏蔽，不重复报警；
3. **流量协调与故障隔离**（主判据，`isolation.py`）：同一路油上串联的体积流量计、按密度（按油温修正）换算成体积的
   质量流量计，以及仿真模型按转速、油温给出的预期流量（不依赖任何流量计的“真实流量参照”），一起检验以下假设：
   无故障、某只表偏、两只表同时偏、供回油之间泄漏、回油夹气、供油侧整体偏、回油侧整体偏、全部体积表共模偏
   （如油品粘度变化）、实际流量与模型预期不符（被试泵出力变化）。每个假设做加权最小二乘拟合，
   得分 = χ² + 每个原因的先验代价（简约性），取得分最低的解释，并给出它的**可能性**和概率不可忽略的**其他解释**。
   各表有健康基准时先扣除它在当前流量、油温下的固有偏差，噪声按各表的基准离散加权；
   - 两只表同时坏时不会把好表也拖下水（旧的“与其余表中位数比较”会被坏表污染）；
   - “供油侧三只表都偏高”与“泄漏”在流量计上表现相同，靠模型的预期流量区分；没有模型时取更常见的泄漏，
     并把另一种解释和它的概率列在“其他可能”里；“全部体积表一致偏低”与“质量流量计偏高”同理；
4. **变点检测**（`changepoint.py`）：稳定段内各表的相对读数突然变化（中途突发故障）或开始逐渐变化（磨损、泄漏扩大）时，
   给出变化开始的时刻，并只用变化之后（渐变取末段）的数据判断当前状态；健康数据中小流量时个别表的缓慢游走不算变化；
5. 质量-体积校核：密度默认用健康基准拟合的密度-温度关系；**换油品或换批次后**，在工作台“数据目录”或“自动诊断”页
   填写当前燃油的 20 ℃ 密度（合格证上的值），否则可能误报质量流量计异常；
6. 零点：无流量管路上流量计应接近 0；
7. 原经验公式（质量流量→涡轮转速→理论流量，`app/core/flow_meter.py`）只在报告中作参考；
8. **模型残差**：按实测工况查仿真基准表，与健康参考模型的预期值比较（见下方“仿真模型”），
   发现各表一致但整体偏离（被试泵出力变化）和没有冗余表的压力测点偏离。

结论分四级：正常 / 预警 / 异常 / 无法判定。阈值（`bench.json`）：单表偏差预警下限 1.3%、供回油平衡预警 1.2%、
质量-体积预警 1.5%，有健康基准时取 max(下限, 4×基准离散)。2026-11 的 60 个健康文件上无一误报（最大偏差为预警阈值的 0.9 倍），
单表漂移约 0.75–2% 可检出，泄漏约 1.25–1.5% 可检出。

**原因分析**（`causes.py`）：故障隔离给出的每个原因直接成为报告中的一个原因（并入同一对象的渐变、噪声、毛刺），
附解释、判断依据、可能性、其他可能和处理建议；模型发现的系统性偏离用模型检查给出的结构化依据
（与流量相关的压力是否同步变化）区分“实际流量变了”和“测量整体偏了”。

**历史趋势**（`history.py`）：每次诊断后与同类来源（试验台实时/自动诊断，或手动选择的文件，两类分开）近 90 天的
诊断结果对比：某只表、供回油差或质量流量计的偏差最近几次比最早几次变化超过 1% 时提示长期漂移；如果历次结果还
**一直朝同一个方向走**（秩相关 ≥ 0.7），说明是持续发展的漂移，升为预警——本次单次检查正常时结论也改为预警。
质量流量计有偏差时，用几次不同流量的结果把误差拆成零点（kg/h）与标定（%）两部分。任务列表页“诊断趋势”可查看
各表偏差随时间的变化。

报告包括结论、原因分析、检查项、检测明细、处理建议，以及算法版本、配置与健康基准来源。

**配置**（`pump_test_bench/config/bench.json`，修改后下次诊断即生效）：管路与流量计的对应关系、各表对应的
三维部件、密度-温度模型、各项阈值、传感器合理范围。当前对应关系是按 2026-11 实测数据推断的，请对照管路图核对。

**健康基准**（`baseline.py`）：用设备正常时的数据，统计每只流量计相对其余表的固有偏差（拟合为流量、油温的函数）、
短时波动，并拟合密度-温度关系。随代码提供的 `config/baseline_default.json` 由 2026-11 的 60 个工况文件生成；
设备检修、更换流量计后应重新建立：

```bash
python -m pump_test_bench.tools.build_baseline 健康数据目录 --save      # 保存到 pump_test_bench/data/baseline.json
python -m pump_test_bench.tools.validate_diagnosis 健康数据目录          # 故障注入验证：检出率、定位准确率、误报率
python -m pump_test_bench.tools.generate_fault_data 健康数据目录 --out 故障数据  # 生成 15 类物理故障的异常数据文件（原格式）+ 故障清单.csv
```

### 仿真模型（`pump_test_bench/app/simulation/`）

仿真模型是试验台各部分的**健康参考模型**：给定工况，给出健康时各测点的预期值，诊断时与实测比较。
每个模型一份配置（`config/simulation/<id>.json`），各有一张仿真基准表并用正常数据标定。

**物理量映射（`config/signals.json`）**：按标准台原理图把系统 → 物理量 → 采集列 → 三维部件对应起来，诊断、仿真和三维显示都按这张表。
三维部件与系统的对应：油箱系统 = 循环油箱，离心泵驱动电机 = 离心泵·油路块，供油系统 = 供油管路，传动系统 = 被试件 2（电传），
被试件（高压泵）= 被试件 1，回油系统大流量管路 = 回油流量计 1，小流量管路 = 回油流量计 2。
以下几处按数据推断、标为“待确认”，如与现场不符，改 `signals.json`、模型配置和前端 `components.js` 即可：

| 物理量 | 采集列 | 依据 |
|---|---|---|
| 油箱供油压力 | P13燃油油箱压力 | 数据中恒为 −0.375，按绝对偏差判断 |
| 总流量计 | 齿轮流量计 | 无同名列 |
| 被试件出口压力 | P5低压压力 | P2/P3/P4 数据中约为 0 |
| 回油质量流量1（大流量管路） | 回油质量流量2 | 数据中大流量管路工作时只有该列有读数，与表格命名相反 |
| 回油质量流量2（小流量管路） | 回油质量流量1 | 同上 |
| 回油压力1-1 | 回油压力1-1 | 数据中恒为 0.048，低于 1-2，可能未接或量程不同 |

派生测点：涡轮流量计转速 `回油流量x-x转速`（Hz）由回油流量按 q = K·f + q0（默认 K = 0.304921、q0 = 0.210230，L/h）反算。
K、q0 可在“仿真模型”页右上角“派生测点”中修改（保存在数据库目录 `signals_derived.json`），前端三维与工作台同步使用；改后用到它的模型需重建。

**两类模型**：
- **内置模型**：随代码提供（`config/simulation/*.json`）。计算公式只写在后端配置文件中，**页面上不显示、不能修改**；
  页面上可以调整它的诊断方案、阈值倍数、适用条件、对应测点等，修改保存时后端按输出名称保留原公式。
- **页面上新建的模型**有两种方式：**数据拟合**（由正常数据拟合，建立时只选正常数据目录）和 **仿真**（AMESim：填写模型文件、
  参数映射与输出变量，建立时逐个工况仿真）。

| 内置模型 | 方式 | 变量 → 输出 | 适用条件 | 负责发现 |
|---|---|---|---|---|
| 标准台系统模型 `bench` | 数据拟合 | 电传转速（主变量）、电机转速（次变量）、油温（环境变量）→ 油箱、供油、被试件、大流量回油各物理量 | 大流量管路工作 | 被试泵出力下降、无冗余的压力传感器漂移 |
| 涡轮流量计模型（大流量管路）`turbine_large` | 内置公式 | 质量流量、介质密度 → 两只涡轮表转速 Hz | 大流量管路工作 | 单只/两只涡轮表 K 系数漂移；参考量（质量计、密度）偏差 |
| 涡轮流量计模型（小流量管路）`turbine_small` | 内置公式 | 同上（小流量管路） | 小流量管路工作 | 同上。现有正常数据中小流量管路无流量，待有数据后建立 |

**内置公式**（输出配置 `"method": "formula"`，只在后端配置文件中写）：变量名、系数、+ − × ÷ ^、exp、log、sqrt、min、max、clip、if 等，
系数 `"fit": false` 固定、`true` 由正常数据拟合；只做白名单解析，不执行代码。涡轮流量计用用户回归结果
`a + b·质量流量 + c·密度`（a = 934.79，b = 13217.85，c = −1.18；质量流量 kg/s 由采集的 kg/h 换算，密度由油温换算），系数固定。
它与按 K 系数反算的转速平均相差约 +12%，页面上提示核对；诊断时作为固有偏差扣除，扣除后离散约 0.8–0.95%。

**数据拟合**：按变量角色确定结构——主变量最高三次、次变量二次、环境变量（油温等）一次，加交叉项——由正常数据拟合。
角色可手动指定或按数据建议。2026-11 数据上，换油温段的平均误差由原二次响应面的 1.49% 降到 0.91%
（让算法自由挑项在嵌套验证中不稳定，高斯过程等黑箱换油温更差，故不采用）。拟合结果保存在后端，页面上只显示精度。
- 变量可以是测点、多个测点的中位数、由油温算的燃油密度/运动黏度、常数，并可按“× 系数 + 偏移”换算单位（如 kg/h → kg/s）。
- **检验**（页面“精度”页）：按油温目录留一交叉验证的误差、与“用平均值”比较、各油温段误差；列出可疑样本（稳健 z > 4），
  由用户勾选排除后重建；给出建议（恒定输出按固定值比较、无关输出建议移除、内置公式与现场相差 > 5% 提示核对）。
- 编辑页“试拟合 / 验证精度”用某个正常数据目录试算，不保存。
- 数据拟合与内置公式的模型诊断时直接计算，不建网格；变量超出建模数据范围时提示“外推”。仿真模型在网格上仿真、插值。

- **标定**：用正常数据求每个测点的固有偏差（随工况平滑变化）与离散 σ；由数据拟合的输出按交叉验证残差估计 σ，阈值 = max(下限, 倍数 × σ)。
  2026-11 数据（自动拟合）：系统流量 σ≈0.55–0.8%，压力 0.8–2.8%。
- **残差**：每个输出可选相对（偏差 ÷ 预期）或绝对（直接相减，用于温度和接近 0 的量），绝对模式用 `floor_warn_abs`/`floor_alarm_abs` 下限。
- **规则**：单测点偏离；整体偏移（一组测点彼此一致、整体偏离，含义分 pump / reference / input 三种）。
  模型的发现并入原因分析：属于已有原因的作为补充依据，否则单独成为原因。
- **诊断方案**：每个模型“参与结论 / 仅作参考 / 关闭”，以及预警、异常的 σ 倍数。全局一套（“仿真模型”页），
  自动诊断与手动诊断共用；手动诊断时可在“自动诊断”页临时调整。
- **模型管理**：“仿真模型”页左侧为模型列表（状态、方式、换油温误差），右侧为所选模型（诊断方案、精度、变量与输出、标定、工况试算），可编辑、删除、重建。
  所有模型都可以删除；内置模型删除后不参与诊断，可从右上角“恢复已删除的内置模型”恢复（记录在数据库目录 `simulation_models/_deleted_builtin.list`）。
  自定义模型保存在数据库目录 `simulation_models/`；内置模型也可以在页面上修改（保存为同名自定义配置，可恢复内置配置）。
  改了变量、输出或后端公式后原结果作废，重建前该模型不参与诊断。

**扩展**：代理模型构建方法（如基于大模型提出公式）、仿真引擎、诊断分析器、诊断推理器（如大模型智能体）都有固定接口，
写成插件模块并列入 `config/plugins.json` 即可，不改核心代码。见 [docs/扩展指南.md](docs/扩展指南.md)。

```bash
python -m pump_test_bench.tools.build_simulation_table 健康数据目录                    # 所有模型，保存到数据目录
python -m pump_test_bench.tools.build_simulation_table 健康数据目录 --model turbine_large    # 只建一个模型
python -m pump_test_bench.tools.build_simulation_table 健康数据目录 --default          # 写入随代码提供的默认结果（显示各输出公式与误差）
```

## 安装包部署（推荐给现场电脑）

用 `deploy\windows\build_installer.ps1` 一键生成 Windows 安装包 `BenchCheck-Setup-<版本>.exe`，目标电脑双击安装即可使用，
不需要安装 Python、Node.js、Nginx；系统开机自动在后台运行，升级时配置与数据保留。
**打包与安装的操作步骤见 [deploy/windows/README.md](deploy/windows/README.md)**（开头“操作步骤”一节照着做即可）。
**改了代码以后重新打包：双击项目根目录的 `打包安装包.bat`。**

开发电脑上也可以一条命令运行全部服务（含统一入口，代替 Nginx，需先编译前端）：
`python -m pump_test_bench.app.services.supervisor`，然后打开 http://localhost:8080。

## 快速开始（Windows，开发）

1. **配置**：复制 `.env.example` 为 `.env`，至少填写 `SECRET_KEY`、`ADMIN_PASSWORD`。数据目录在前端填写，不需要改 `.env`。
2. **后端**：
   ```powershell
   conda env create -f pump_test_bench/environment.yml   # 首次
   powershell -ExecutionPolicy Bypass -File pump_test_bench/start_project.ps1
   ```
   也可以在仓库根目录分别运行 `python -m pump_test_bench.app.services.task_service`（以及 `file_service`、`llm_service`）。
3. **AMESim 服务**（只在用 AMESim 重建仿真基准表时需要）：设置环境变量 `AME`，运行 `AMESim_server/startAmeServer.bat`，模型文件放在 `AMESim_server/model/`。
4. **大模型**（需要智能助手时）：按 `DeepSeek-model/README.md` 部署 Ollama。
5. **前端**：
   ```bash
   cd digital-twin-platform
   npm ci
   npm run dev          # 开发，http://localhost:9528
   npm run build:prod   # 生产构建，配合 deploy/nginx.conf
   ```
   新版 Node（17 及以上）需先设置 `$env:NODE_OPTIONS = "--openssl-legacy-provider"`。

## 测试

**实时故障诊断测试**：双击仓库根目录的 `测试实时诊断.bat`，模拟试验台按时间一行一行往目录里写数据（正常数据 + 注入了故障的数据），
在系统工作台把数据目录设为该目录并打开自动诊断，即可在页面上查看实时显示与诊断结论，对照生成的数据清单（预期结论）。
说明见 [docs/实时诊断测试说明.md](docs/实时诊断测试说明.md)。

```bash
cd digital-twin-platform && npm run lint && npm run test:unit
```
